# TerraMind — ИИ-почвовед

## Запуск

Python 3.12+, Ollama и установленные модели:

```sh
python -m venv .venv
# Linux/macOS: source .venv/bin/activate
# Windows: .venv\Scripts\activate
python -m pip install -r requirements.txt
ollama pull gemma4:12b-it-qat
ollama pull bge-m3
python api.py
```

Ollama должен работать локально (обычно это делает приложение Ollama;
на Linux можно запустить `ollama serve` отдельно).

### Публичный запуск на Windows

Запускайте `запуск.bat`. Он переходит в каталог проекта и использует Python
из `.venv`, если это окружение создано. Рядом должен находиться `cloudflared.exe`
(либо `cloudflared` должен быть установлен в PATH). Существующий
`CLOUDFLARE_TUNNEL_TOKEN` хранится в локальном `.env`.

Скрипт сначала загружает настройки, затем проверяет локальный API и запускает его,
если он ещё не работает. После этого запускается туннель с протоколом `auto`
(QUIC с автоматическим переходом на HTTP/2) и явным IPv4. Подключение подтверждается
через локальный `/ready` cloudflared. Логи непрерывно читаются, чтобы переполненный
канал вывода не блокировал процессы. Вывод API и сообщения запуска видны в основном
окне и сохраняются в `logs/startup.log`; журнал туннеля — в `logs/cloudflared.log`.
Папка и журнал запуска создаются ещё до проверки токена и запуска API: ранняя
ошибка тоже остаётся в файле. Токен Cloudflare и пароли в URL скрываются.
При штатном запуске отключён HTTP access-log, чтобы не записывать в журнал
IP-адреса посетителей и полные ссылки на результаты вопросов. Ошибки запросов
содержат только короткий префикс ID. Журналы дописываются, предыдущие записи сохраняются.
Немедленное завершение API
показывается с кодом выхода отдельно от истечения времени ожидания.
Enter в окне запуска останавливает только процессы, запущенные этим скриптом;
ранее работавший API остаётся запущенным.

Параметры можно изменить в `.env`:

```dotenv
CLOUDFLARED_PROTOCOL=auto
CLOUDFLARED_EDGE_IP_VERSION=4
CLOUDFLARED_METRICS_PORT=20241
```

Протоколы: `auto`, `quic`, `http2`; версии IP: `auto`, `4`, `6`.
Порт метрик доступен только на `127.0.0.1`. Перед повторным запуском остановите
предыдущий туннель; при занятом порте скрипт сообщает об этом.

Если публичный сайт работает только с VPN на компьютере-сервере:

1. Остановите предыдущий запуск, выключите VPN и запустите `запуск.bat`.
2. Если соединение не подтвердилось, запустите `проверка_соединения.bat`.
   Она выполняет проверки именно на вашем ПК: локальный API, локальную Ollama,
   состояние туннеля, публичный API по домену и TCP-доступ к двум адресам Cloudflare
   на порту 7844. Это различает разрыв туннеля и проблему доступа к домену из браузера.
3. Сравните вывод проверки с результатом при включённом VPN.

По [документации Cloudflare](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/deploy-tunnels/tunnel-with-firewall/),
туннель использует исходящий порт **7844**: UDP для QUIC и TCP для HTTP/2.
`auto` выбирает доступный транспорт, но не переносит туннель на порт 443.
TCP-проверка не проверяет UDP и TLS/SNI: открытый TCP-порт сам по себе ещё не
подтверждает рабочий туннель. Ответ HTTP 403 по домену также не означает разрыв
туннеля: он может быть вызван правилами доступа на стороне сайта.
Если доступ блокируется для обоих транспортов,
решение — другой способ соединения с публичным сервером или другой туннель.
Доступность вашей домашней сети нельзя установить по проверке из облака.

Сайт и API обслуживает `api.py` на порту 8000. `backend.py` — старый демонстрационный
сервер с готовыми ответами; загрузку фото и очередь обслуживает именно `api.py`.
Reranker `BAAI/bge-reranker-v2-m3` используется, если его веса уже есть в локальном
кэше Hugging Face. Его можно заранее загрузить командой:

```sh
python -c "from sentence_transformers import CrossEncoder; CrossEncoder('BAAI/bge-reranker-v2-m3')"
```

Если reranker не установлен, ответы продолжают работать через гибридный поиск
и проверку достаточности контекста. Загрузка больших весов не выполняется посреди
пользовательского запроса. Для подключения заранее скачанных весов из отдельного
каталога задайте `RAG_RERANKER_MODEL` перед запуском.

Для выбора другой установленной модели задайте переменные окружения `OLLAMA_MODEL`
и `OLLAMA_VISION_MODEL` перед запуском. Модель для фотографий должна поддерживать
изображения. Примеры переменных есть в `.env.example`; сам API читает их из окружения.

## Скорость ответа

При запуске API начинает загрузку установленного reranker и короткий пробный
расчёт в фоновом рабочем потоке. Страницы сайта, схема API и проверка туннеля
доступны во время подготовки. Вопросы принимаются в FIFO-очередь и ожидают
подготовки; интерфейс показывает «ИИ готовится к работе». Подготовка и ответы
выполняются одним рабочим процессом очереди, поэтому параллельной повторной
загрузки этой модели при первом вопросе нет.
`запуск.bat` ждёт HTTP-готовности API до трёх минут перед подключением туннеля,
не дожидаясь завершения подготовки модели. Вывод виден в окне запуска и
`logs/startup.log`. Большие веса автоматически не скачиваются.
Для отложенного запуска можно задать `RAG_PRELOAD=0`: тогда загрузка
снова попадёт в первый запрос с локальным поиском. Неустановленный reranker
не мешает запуску: остаётся гибридный поиск. Прогрев reranker не прогревает
модели Ollama, которым всё ещё может потребоваться своя первая загрузка.

Результаты успешного локального поиска для одинаковых вопросов используются
повторно в течение пяти минут. Кэш ограничен 64 записями в памяти процесса,
содержит хеш вопроса и найденные материалы, без текста вопроса и без фото.
Истечение срока проверяется при обращении к кэшу. Обновление индекса через
административные маршруты сбрасывает кэш; сбои поиска и reranker не кэшируются.
Срок актуальности задаётся `RAG_CACHE_TTL_SECONDS`, значение `0` отключает кэш.
Параметры экземпляра retriever не следует менять во время его работы.
Готовый ответ не кэшируется: модель отвечает заново, а необходимый веб-поиск
продолжает выполняться. Новый вопрос всё ещё требует расчёта reranker;
эти изменения уменьшают первую загрузку внутри вопроса и повторные расчёты.

Приложение просит Ollama сохранять модели чата, фото и эмбеддингов в памяти
на 30 минут после запроса. Это уменьшает повторные загрузки после простоя.
Первый запрос всё равно может ждать загрузки; при нехватке памяти Ollama может
выгрузить модель раньше. Удержание моделей увеличивает время занятия памяти.
Период задаётся переменной окружения `OLLAMA_KEEP_ALIVE_SECONDS` до запуска API:
`1800` — 30 минут, `0` — выгрузка после каждого запроса, `-1` — без срока.

Reranker использует настройки потоков PyTorch для текущего компьютера.
Прежнего принудительного ограничения четырьмя потоками нет. Для ручного
подбора можно задать `RAG_CPU_THREADS` положительным целым числом. GPU в
`ollama ps` относится к модели Ollama; отбор фрагментов через PyTorch может
работать на CPU независимо от этого.

После каждого запроса окно API выводит строки `[timing …]`:

- `queue` — ожидание своей очереди; `processing` — обработка; `total` — их сумма.
- `agent_init` — инициализация поиска и графа, преимущественно при первом вопросе.
- `local_search` — весь локальный поиск; внутри него `vector_search` включает
  эмбеддинг, `reranker_init` — получение/загрузку reranker, `rerank` — его расчёт.
  `local_cache_hit` означает повторное использование результата локального поиска.
- `classify`, `context_check`, `catalog`, `greeting`, `answer`, `photo` —
  соответствующие вызовы модели; `web_search` — поиск в интернете.
- В скобках у вызова модели: `load_s` — загрузка модели, `prompt_s` — обработка
  входа, `generate_s` — генерация, а также число входных и выходных токенов,
  если Ollama вернула эти сведения.

Вложенные этапы входят в длительность родительского: их нельзя складывать
повторно. Эти строки содержат только время, счётчики и первые восемь символов
случайного ID запроса. Текст вопроса, фото и ответ в них не записываются.
Отключение замеров: `PERFORMANCE_LOGGING=0` перед запуском API.

Для сравнения отправьте один и тот же вопрос дважды без паузы. Если долго
только в первый раз и велико `load_s`, причина — загрузка модели. Если велико
`rerank`, нужно подбирать CPU-потоки; если `web_search` — проверять поиск и сеть.
Короткий тест на три выходных токена не предсказывает время полного ответа
с обработкой музейных материалов, несколькими вызовами модели и веб-поиском.

## Поиск и ответы

Поиск по музейной базе объединяет векторную близость и BM25 с нормализацией
русских слов, «е/ё» и учётом заголовков. При недоступности модели эмбеддингов
сохраняется поиск по словам. Reranker получает заголовок вместе с текстом и
использует явно нормализованные оценки; в ответ можно передать до шести
фрагментов вместо трёх. Общий размер контекста ограничен.

Точные совпадения по редким названиям и предметам вопроса сохраняются даже при
низкой оценке reranker: низкая оценка модели не означает отсутствия факта в книге.
Локальный файл `Video Project 9.txt` также участвует в поиске по словам, поэтому
пустая или частично заполненная коллекция Chroma не скрывает исходные материалы.
Дубли фрагментов убираются; исходная база при этом не меняется и не пересоздаётся.

Перед ответом модель проверяет, хватает ли материалов для всех частей вопроса.
Если нет, запускается веб-поиск. Просьбы «найди в интернете», «последние
исследования» и подобные запускают его даже при наличии текста в музейной базе.
Музейные материалы и найденные веб-фрагменты поступают в ответ совместно.
Исторические факты о музее отделены от общих научных пояснений.
Если история экспоната есть в локальных материалах, ответ строится по ним;
выход в интернет можно запросить явно. При поиске истории музея отбрасываются
страницы одноимённых музеев, не связанные с почвами и монолитами.
Отсутствие локального результата не заменяется автоматически страницами чужих
музеев и не трактуется как доказательство отсутствия экспоната в коллекции.

Используется актуальный пакет `ddgs` с доступными поисковыми провайдерами
(`WEB_SEARCH_BACKEND=auto` по умолчанию) и тайм-аутом 15 секунд на сетевую попытку.
Общий вызов может длиться дольше, если пакет переключает провайдеров; прежнего
внешнего ограничения в 8 секунд нет. Сбой поиска показывается отдельно от
отсутствия результатов. В ответе отображаются метки источников и настоящие
кликабельные ссылки; содержимое модели вставляется как текст, без исполнения HTML.

Для диагностики используйте логи сервера. Для тестовой копии Chroma можно задать
`RAG_DB_PATH`; модель эмбеддингов выбирается через `OLLAMA_EMBEDDING_MODEL`
(по умолчанию `bge-m3`). При замене модели эмбеддингов нужен совместимый индекс:
не переключайте её для уже заполненной базы без отдельного переиндексирования.
Функция `rag.ask_question()` использует тот же обработчик, что и сайт.

## Фотографии и очередь

В ИИ-чате нажмите «Фото» рядом с полем сообщения, проверьте превью и нажмите «Отправить».
Вопрос можно добавить или оставить пустым. Поддерживаются JPEG, PNG и WebP
до 5 МБ и 20 мегапикселей. Сервер проверяет содержимое файла, учитывает поворот
камеры и отправляет нормализованное фото в мультимодальную модель Ollama.
В учебных и музейных вопросах описание используется вместе с вопросом и базой
знаний; отвечающая модель также получает само фото текущего запроса. В определении
участка фотоописатель выделяет ограниченные видимые признаки и качество снимка.
Признак участвует в справочной гипотезе только после отдельного явного подтверждения
посетителем; «да» подтверждает один заданный признак. [Подробности и локальный прогон
с единым отчётом по времени каждого фото](docs/soil-photo-confirmation.md).
Сохраняются до четырёх описаний и структурированных записей фото, их хеши и слова
посетителя отдельно от ответов ИИ. Исходные фото в истории сайта не хранятся.

Для определения почвы участка помощник ориентируется на опубликованную российскую
классификацию и просит одно полезное уточнение за ход. Домашний осмотр рассчитан
на действия суммарно до 10 минут без специального оборудования и обязательных
покупок. pH спрашивается только при наличии подходящего теста; по фото он не
вычисляется. Если признаков недостаточно для конкретного типа, ответ остаётся
предварительным и называет следующий различающий признак.

Все посетители используют одну FIFO-очередь: запросы обрабатываются строго по
одному, в порядке поступления. Сайт показывает реальное число запросов впереди,
затем статус обработки и ответ. Повторная отправка блокируется до завершения.
После обновления страницы ожидание восстанавливается в той же вкладке.
При временной потере связи сайт продолжает проверять тот же запрос.

- `POST /ask/jobs` — JSON `{"text": "Вопрос", "image": "base64 без префикса"}`;
  отвечает `202` с `job_id`, `status`, `ahead`.
- `GET /ask/jobs/{job_id}` — `queued`, `processing`, `done` (с `answer`)
  или `failed` (с `error`). Идентификатор случайный; не передавайте его другим людям.
- `POST /ask` — совместимый прежний API с ожиданием ответа, использует ту же очередь.
- Неверное фото — `400`, превышение размера — `413`, заполненная очередь — `429`.

Очередь хранится в памяти одного процесса: запускайте **один worker Uvicorn**.
Максимум 20 ожидающих запросов; результат хранится 15 минут после завершения.
Фотография освобождается после обработки и не сохраняется в истории.
Перезапуск сервера очищает очередь; сайт предложит отправить вопрос заново.
У запросов к Ollama установлен сетевой тайм-аут 240 секунд на вызов. Ожидание
в очереди не удерживает длинное HTTP-соединение. Разрыв клиентского соединения
не освобождает занятое моделью место и не запускает параллельную обработку.

`app.db` и `chroma_db_new` содержат данные приложения. Для пробных запусков
используйте копию проекта, чтобы не изменить исходные данные.

## Проверки

```sh
python -m unittest discover -s tests -v
```

Тесты используют временную SQLite-базу и управляемые модели: проверяют передачу
изображения, очередь, API, русский поиск и отбор контекста, маршрутизацию в интернет,
сохранение одновременно местных и веб-источников, ссылки и различие между сбоем
поиска и отсутствием результатов. Загрузка весов Ollama/Hugging Face не требуется.

## Каталог почв

На главной странице представлены 48 образцов из фотографий музейных табличек.
Поиск работает по названию, месту, году и другим сведениям; есть фильтр по
группам почв. У каждого образца отдельная ссылка `/soils/001/` … `/soils/048/`,
фотографии монолита и таблички, описание и характеристики. Кнопка
«Скачать описания» сохраняет полный текст каталога.

Данные редактируются в `static/data/soils.json`; после изменения выполните
`python scripts/build_catalog.py`. Сгенерированные страницы уже включены
в проект, поэтому при обычном обновлении запуск генератора не нужен.
Источники, правила сопоставления и обнаруженные расхождения перечислены в
[отчёте об импорте](docs/soil-catalog-import.md).

## Аккаунты, сохранённые чаты и память

На сайте доступны регистрация, вход, список сохранённых бесед и их удаление.
Чаты аккаунта сохраняются в `data/app.db` и остаются после перезапуска сервера.
«Новый чат» сохраняет прежнюю беседу в списке. ИИ учитывает ограниченную часть
последних сообщений именно выбранного чата и описание последнего фото.

Без входа работает временная память на 30 минут бездействия, без записи новых
гостевых сообщений в SQLite. Это ограничение не удаляет чаты аккаунта.

При первом запуске существующая `app.db` автоматически копируется в `data/app.db`;
оригинал сохраняется, а уже созданная новая база не перезаписывается. Не удаляйте
папку `data/` при обновлении и не коммитьте рабочие базы. Пароль восстановления
по email пока не отправляется — сохраняйте пароль аккаунта.

Политика: `/privacy/`; условия: `/terms/`.
[Порядок обновления, хранения, удаления и ограничения](docs/conversation-memory-and-privacy.md).

## Пароли и предупреждение Chrome

В аккаунте появилась кнопка «Пароль»: можно заменить пароль без удаления бесед.
При регистрации и смене требуется 12–128 символов; типичные слабые варианты
отклоняются. Старые аккаунты продолжают входить со своим прежним паролем.
Если Chrome нашёл его в утечке, замените его на уникальный и сохраните обновление
в менеджере паролей браузера. Сайт не отключает проверку утечек Chrome.

### Отзывы, лимиты и администраторы

Обычным аккаунтам доступны 5 запросов в день; первый приватный отзыв об ИИ с комментарием даёт ещё 5 до конца дня. Администраторы освобождены от суточного лимита. Назначение роли на сервере, правила бонуса, ограничения гостевого режима и настройка фонов: [инструкция](docs/feedback-and-limits.md).

### Структурированное определение почвы

Диалог сохраняет сообщённые признаки и выбирает уточнения без повторения известных и неизвестных полей. Подключены десять [справочных направлений с источниками](docs/soil-reference-rules.md): в итоговом ответе видны основания, недостающие признаки и необходимые проверки. Это исследовательские гипотезы, ещё не подтверждённые независимым почвоведом; автоматического установления типа и измерений по фото нет. Учебные ответы и музейный каталог работают отдельно. [План, ограничения, проверка версии сервера и диагностика поиска](docs/soil-diagnosis-roadmap.md).

Исправления по повторным десяти сценариям: [смысл наблюдений, контекстные уточнения и обязательные критерии гипотез](docs/soil-evidence-fixes.md). Версия `/health` — `semantic-soil-interview-v4`.
